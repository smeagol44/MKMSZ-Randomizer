## Release definition

MKMSZR 1.0 is **not** complete with the current stage-local pickup shuffle alone. The release boundary requires a deterministic global run model that can place ordinary randomized items across the eight main stages, reject unwinnable layouts deterministically, present enough run state to the player, preserve the required run resources and invariants across lifecycle boundaries, and pass representative full-seed runtime validation.

Current implementation maturity is not itself a requirement. A feature may already be Production/Production beta while still needing a final 1.0 acceptance gate, and a runtime proof does not automatically make a proof-only mechanism part of the product pipeline.

Evidence terms on this page retain their existing project meanings: **Runtime-confirmed**, **Static-confirmed**, **Implementation/CI-confirmed**, **Hypothesis / strong inference**, **Rejected / failed**, and **Pending**.

## Required 1.0 behavior

### R1 — Global cross-stage ordinary-item randomization

1.0 requires one global logical ordinary-item pool across the eight main stages rather than eight independent stage-local shuffles.

The current ordinary-pickup catalog contains **84** ordinary `0x30`-byte records. The Temple Map is not one of those 84 records and is handled separately under R7.

A global placement cannot blindly copy the source record's movable identity tuple into another stage. The destination-stage materialization path must preserve the randomized item's actual identity, including:

- correct award semantics through a destination-safe callback/parameter path;
- correct collision/extents and presentation descriptor where required;
- the item's actual visual/model identity;
- a destination-local resource selector that resolves to the required resource;
- a guarded imported resource bundle when the destination does not already contain an equivalent resident resource.

A temporary design that awards item A while deliberately showing destination item B is **not acceptable for 1.0**.

The production materializer must also enforce guarded storage/allocation bounds, destination selector planning, file-table/resource updates where required, and deduplication rather than assuming an empty logical selector is free physical storage.

**Current state:** **Pending for production integration.** Cross-stage feasibility is Runtime-confirmed in bounded proofs. The generalized pure resource planner is implemented but disconnected from the normal browser/CLI pipeline. Prison is Runtime-confirmed with five simultaneous imported visuals plus an untouched Herbs control; the equivalent Fortress stress route is still pending manual runtime validation. Destination-safe key/crystal award handling also remains pending.

**Acceptance criterion:** a normal product build can materialize the global logical assignment into all affected destination stages with correct item visuals and awards, guarded bounds, and no reliance on proof-only allocation. The composed planner gate and destination-safe key/crystal path must be validated before global materialization is enabled in the browser/CLI product pipeline.

### R2 — Deterministic global generation and deterministic retry attempts

The current stable SHA-256/Fisher-Yates approach remains the deterministic model, but 1.0 must apply deterministic generation to the global logical run rather than eight independent stage-local pools.

Rejected candidate layouts must not mutate hidden RNG state in a way that changes future regeneration. Retry state must be explicit. The required contract is conceptually:

```text
candidate = H(namespace || user_seed || attempt_index || counter)
```

Attempt 0 is tested first, then attempt 1, then attempt 2, and so on until an accepted layout is found. Under the same MKMSZR version/rules, the accepted attempt and final layout must therefore be pure functions of the displayed seed.

Unrelated deterministic namespaces — including boot phrases, palette selection, HUD flavor text, progression-reward selection, or the required-Power-Upgrades target — must not advance the layout retry sequence.

The current stage-local implementation's 1,000-attempt ceiling is an implementation detail of the interim mode. No separate 1.0 global retry limit is established by the current requirement sources.

**Current state:** **Pending** for the global generator. Deterministic stage-local generation and deterministic rejection attempts are Implementation/CI-confirmed; the legacy Lua global loop is only a design reference and contains a known retry/reseeding flaw.

**Acceptance criterion:** regenerating the same seed under the same 1.0 rules produces the same accepted attempt and byte-identical logical global layout even when one or more earlier candidates are rejected, and unrelated RNG features cannot alter that result.

### R3 — Deterministic whole-run solvability validation

Every accepted 1.0 global layout must pass a whole-run progression validator before it is materialized as the final seed.

The validator must use the current researched stage/location requirements as its rules source. The legacy Lua fixed-point solver is useful for the overall algorithmic shape — repeatedly collect all currently accessible locations until no new location opens — but its access rules and final beatability predicate are stale/incomplete and are not authoritative for native 1.0.

The completion predicate must include the seed-specific required number of Power Upgrades. The 1.0 product retains the concept of exactly nine progression rewards existing in the world while a seed independently determines how many of those rewards are required for completion.

The required-Power-Upgrades target must:

- be generated deterministically from its own RNG namespace;
- be independent of global-layout retry count;
- be represented in the whole-run solver's completion predicate;
- be visible to the player through the randomizer HUD;
- preserve the current runtime-confirmed native threshold behavior for each collected progression reward.

The exact allowed minimum/maximum policy for the required count is **still Pending** and must be finalized with the global solver; this page does not invent that range.

**Current state:** **Pending** for the whole-run validator and seed-specific required-count policy. The current stage-local access rejection loop is Implementation/CI-confirmed. Native progression behavior is Production beta and Runtime-confirmed through XP 258/two tiers on bounded lifecycle routes; all nine reward tiers have not yet been completed in one runtime run.

**Acceptance criterion:** every emitted 1.0 seed has been accepted by a deterministic fixed-point whole-run validator using the finalized current access rules and completion predicate, including the independently generated required-Power-Upgrades target. The same user seed and rules must produce the same solver result and accepted attempt.

### R4 — Native randomizer HUD

1.0 requires a native in-game HUD/UI that exposes the run state needed to play the seed. The legacy Lua overlay is a semantic reference only; exact visual parity and the Lua inventory implementation are not required.

Required information is:

- current check progress, including collected/total information useful for the current stage;
- required Power Upgrades and the player's current progression status;
- current inventory storage navigation state;
- key-item progress by stage;
- useful temporary pickup feedback.

The old Lua overlay called its storage indicator an inventory “page.” The native product instead uses four authoritative backing boxes. The reconciled 1.0 requirement is to expose the **current native box/storage state**, not to reintroduce Lua paging. The existing Runtime-confirmed `BOX n OF 4` text satisfies only that part of the broader requirement.

A text-first implementation is acceptable if it communicates the required state reliably; geometric icon parity with the Lua overlay is not required.

**Current state:** **Partial.** Native text drawing and `BOX n OF 4` are Runtime-confirmed and Production. The complete randomizer HUD is Pending.

**Acceptance criterion:** during normal gameplay, the player can determine the required run-state information above without external Lua/emulator UI, and the display remains correct across the lifecycle routes covered by final 1.0 validation.

### R5 — HP, lives, continues, and run-reset lifecycle

1.0 must define and implement the lifecycle of the **actual current-run** HP, lives, and continues values across:

- normal stage transitions;
- direct Safe Stage Select routes used by the product;
- the relevant title/load/re-entry boundaries;
- Game Over/new-run reset.

The legacy Lua startup writes — Very Hard, six lives, and four continues — are clues only. They do not establish the native current-run storage or prove preservation across stage transitions. Likewise, the Lua's life-related address does not establish a complete native lifecycle solution.

The preserve/reset policy must be established from current native static/runtime evidence, not inferred from the Lua startup configuration.

Game Over/new-game reset behavior is currently Pending for the shared randomizer state as well and must be reconciled with this lifecycle so a new run does not inherit state that belongs to the previous run.

**Current state:** **Pending.** Ordinary pickup persistence, four-box inventory persistence, stage-key masking, and bounded XP persistence are already Runtime-confirmed on documented routes, but the current HP/lives/continues lifecycle has not yet been traced and accepted for 1.0.

**Acceptance criterion:** the intended current HP/lives/continues values survive or reset at every defined lifecycle boundary exactly according to the documented 1.0 policy, including direct selector routes, and Game Over/new run establishes a clean run state.

### R6 — Very Hard invariant

Very Hard must be a **run invariant**, not merely a value selected once at startup.

The legacy Lua writes difficulty value `0x04` during initialization, but that is not evidence that the native product remains locked to Very Hard across all relevant lifecycle paths.

**Current state:** **Pending.**

**Acceptance criterion:** the 1.0 runtime remains on Very Hard throughout the supported run lifecycle and cannot drift to a lower difficulty through the stage/title/direct-selector routes exercised by the product.

### R7 — Temple Map special case

The Temple Map is not one of the 84 ordinary pickup records. Its inventory reward is coupled to Temple-specific scripted behavior, including the elevator/exit path, and stock behavior removes the Map on Temple -> Wind.

The current sources do **not** settle whether the Map must become a randomized **85th check**. They establish that 1.0 must resolve the special case rather than silently treating it as an ordinary pickup.

Before the Map can be included in the global pool, the product must establish:

- whether the logical Map inventory reward can be separated from the Temple elevator/exit trigger;
- how Temple remains completable if the logical Map reward is placed elsewhere;
- how to prevent the randomized logical Map item from being removed by the stock Temple -> Wind cleanup path;
- whether retaining the Map across later transitions has side effects.

Until those points are proven, the global solver must model the Map separately rather than pretending it is an ordinary `0x30`-byte record.

**Current state:** **Pending policy and implementation.**

**Acceptance criterion:** the 1.0 Map policy is explicit and runtime-valid. If the Map is included as a shuffled check, reward/trigger behavior and cross-stage persistence must be safely separated. If it is excluded from the global item pool, the solver/check count must keep that exclusion explicit and Temple's elevator/exit progression must remain correct.

## Blockers and non-blockers

### 1.0 blockers

The following are release blockers under the current requirements:

1. production-safe global cross-stage item materialization, including the remaining composed planner gate and destination-safe key/crystal award handling;
2. deterministic global shuffle and explicit deterministic retry attempts;
3. deterministic whole-run solvability validation, including finalized required-Power-Upgrades policy;
4. native randomizer HUD with the required run-state information;
5. resolved Temple Map 1.0 policy and any implementation needed by that policy;
6. HP/lives/continues lifecycle plus Game Over/new-run reset behavior;
7. enforced Very Hard invariant;
8. representative final full-seed Runtime-confirmed validation after the above are composed.

### Explicit non-blockers

The current project sources explicitly state that these are **not 1.0 blockers**:

- ordinary-enemy randomization;
- Reverse Elbow / foreign-move completion.

Bosses and scripted encounters are also outside the ordinary-enemy system and are not implicitly added to 1.0 by this roadmap.

This page does not classify unrelated donor/presentation experiments as 1.0 requirements unless an owning requirement source explicitly promotes them later.

## Dependency order

The current Project Status priority order gives the following 1.0 dependency chain:

| Order | Gate | Why it comes here |
|---:|---|---|
| 1 | Finish cross-stage resource/materialization production gate | The global logical layout cannot become a playable ROM until destination resources and award semantics can be materialized safely |
| 2 | Replace stage-local generation with deterministic global shuffle + whole-run solver | Generation/solver must operate on the finalized global item/materialization model and include deterministic retries plus required-Power-Upgrades target |
| 3 | Build the native randomizer HUD | HUD should consume the finalized global-run/check/progression state rather than an interim stage-local model |
| 4 | Resolve Temple Map, then HP/lives/continues lifecycle and Very Hard invariant | These are remaining run-lifecycle/progression invariants needed before declaring a whole run release-ready |
| 5 | Run final full-seed validation | Runtime release evidence comes only after the production composition exists |

This ordering is a dependency/prioritization rule, not a claim that every lower item must wait for all design or documentation work above it.

## Final 1.0 runtime-validation gate

The final release gate requires a **representative full global seed** on the normal production composition.

At minimum, that run must demonstrate:

- an accepted deterministic global layout produced by the production generator/solver;
- cross-stage randomized items rendering as and awarding the items actually assigned;
- progression through the complete run without a solver/materialization softlock;
- all **nine** progression reward tiers exercised in runtime;
- the seed-specific required-Power-Upgrades rule behaving as generated and shown in the HUD;
- the required HUD state remaining usable during the run;
- ordinary-pickup persistence and four-box/key-masking behavior remaining healthy in the composed build;
- the finalized Temple Map behavior;
- the finalized HP/lives/continues policy across the major lifecycle boundaries;
- the Very Hard invariant;
- the defined Game Over/new-run reset boundary.

The route must include the major lifecycle transitions relevant to the implemented policies, including normal stage progression and the documented direct/title re-entry boundaries where those systems are expected to survive.

Passing CI/static checks is necessary but does not satisfy this final gate. The completed route is **Runtime-confirmed** only for the tested seed/routes and must not be described as exhaustive proof of every possible 84-location/item combination.

## Known requirement ambiguities still open

These are requirement questions, not implementation facts to be silently guessed:

1. **Temple Map inclusion:** current sources call it a possible 85th check while also requiring 1.0 investigation of its reward/trigger and persistence behavior. Inclusion in the global pool is not yet settled.
2. **Required-Power-Upgrades range:** the deterministic seed-specific requirement is mandatory, but its exact allowed minimum/maximum policy is not yet finalized.
3. **Whole-run completion predicate:** the global validator is required, but the legacy Lua's narrow final predicate is explicitly not sufficient. The finalized native completion predicate must be documented with the global solver.
4. **HP/lives/continues policy details:** preservation is required to be defined from native evidence; the legacy startup values do not answer which current-run values survive each boundary.
5. **Global retry ceiling:** deterministic retries are required, but the interim stage-local limit of 1,000 attempts has not been established as the 1.0 global limit.
